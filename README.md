# JU Hostel Mess Demand Forecasting

Daily meal-demand forecasting and newsvendor cost optimization for three Jadavpur
University hostel messes, with a champion/challenger MLOps loop, calibrated
prediction intervals, and a Next.js operations dashboard.

The forecast is not the deliverable. The **decision** is: given a demand
distribution and asymmetric costs (waste ₹35/meal vs. shortage ₹55/meal), how
many meals should the kitchen cook tomorrow?

---

## Data: what this establishes and what it does not

**This project runs on a simulator, not collected data.** Everything in
`data/` is generated by `backend/data_generation.py`.

The simulator is parameterized from operational experience running the mess at
JU — three hostels, per-meal attendance of roughly 200 / 150 / 50, the Sunday
vegetarian dinner where attendance collapses, the morning-vs-night gap driven by
late-night study habits. Public institutional mess data at daily granularity
does not exist; the closest public sources (weekly food-delivery order counts)
are structurally different, which is why a simulator was built rather than
downloaded.

**What the metrics in this repo measure:** whether the pipeline recovers
structure that was deliberately planted — the Sunday multiplier, holiday and
exam effects, menu-type effects, the Negative Binomial dispersion — and whether
the newsvendor layer sizes quantities correctly given a forecast distribution.

**What they do not measure:** real-world forecast accuracy. A model evaluated
on data generated by an equation the same author wrote is testing the pipeline,
not the world. No accuracy claim is made here.

**How this would be validated:** a pilot week against the actual hostel
attendance registers, then recalibrating the residual distribution from the
empirical errors and keeping the simulator for counterfactuals and cold-start.

`scripts/recovery_test.py` runs the structural-recovery checks directly —
shortage rate, Sunday multiplier, dispersion index — and exits non-zero on
failure.

## Deliberate modelling decisions

These are the choices worth defending, and why.

**No weekday effects.** `WEEKDAY_DEMAND_SCALE` is flat at 1.0 for Mon–Sat. The
observed day-to-day spread across the week did not exceed the Poisson noise
floor at n ≈ 45–200 per meal, so encoding it would have planted structure the
data could not distinguish from counting noise. Only Sunday, which clears the
noise floor by a wide margin, is modelled (`SUNDAY_DAILY_MULTIPLIER = 0.82`).

The generic weekend-departure assumption the code originally carried
(Sat 0.90 / Sun 0.86) was removed because it does not hold at these hostels —
Saturday-night attendance is flat against a weekday.

**Negative Binomial, not Gaussian, terminal noise.** At μ ≈ 50 the normal
approximation puts real probability mass below zero and requires constant
clipping. Count data needs a count distribution. Dispersion index is set to
~1.3 (mild overdispersion), giving Var = μ + μ²/r with r = μ/0.3.

**Scale-free constants.** Every effect in the generator is multiplicative on
occupancy rather than an absolute number of meals. A fixed 12-meal weather
penalty is 0.6% of demand at 2,000 meals and 24% at 50 — the original
hackathon-scale constants were rescaled accordingly.

**Effects applied exactly once.** Menu, holiday, exam, and event effects enter
the demand equation in one place. In the earlier version each appeared both
inside `attendance_variation` and again as an explicit multiplier, so the
realized effect never matched the constant that was written down — which makes
structural recovery untestable.

**Shared campus shock.** Three hostels a few hundred metres apart are hit by
the same festival, the same rainstorm, the same exam week. One shock is drawn
per day and applied to all three, on top of each hostel's independent noise.
Fully independent series would make the panel artificially easy.

**MAR, not MCAR, missingness.** Attendance logs go missing on holidays
(skeleton staff); weather readings go missing during heavy rain. Missingness
probability depends on the data rather than being uniform.

**No degenerate spatial features.** All three hostels share a campus, so
`latitude`, `longitude`, `campus_zone`, and `capacity_band` carry no variance
and were removed from both the tabular feature spec and the TFT encoder.
`kitchen_id` and `capacity` remain — those still separate the series.

**Seasonal-naive baseline.** The "before" comparison is last week's same-weekday
actual demand, not a buffer applied to the model's own forecast. A baseline that
consumes the model output measures only the optimizer and is guaranteed to look
good.

**No annualized ROI.** Extrapolated savings figures were removed. Only
per-day realized cost differences on the holdout are reported, and they are
reported as `null` when the evaluation frame cannot support them.

## Metrics

Scale matters here: the boys' hostel is 4× the girls' hostel, so pooled RMSE
would be dominated by the largest series.

- **WAPE** and **MASE** (seasonal-naive lag-7 denominator) alongside RMSE/MAE.
  MASE < 1 means the model beats seasonal naive.
- **Per-series metrics** — for each hostel: n, mean demand, WAPE, MASE, and the
  **Poisson noise floor** (`√μ / μ`). The noise floor is the irreducible error
  on count data; reporting it next to the achieved error states the ceiling
  rather than hiding it. At μ = 200 / 150 / 50 the floors are roughly
  7% / 8% / 14%.
- **Interval coverage** — empirical vs. nominal 90%, with the calibration gap.
- **Service level** — planned shortage probability vs. the target ceiling, and
  the realized shortage rate.

Champion/challenger promotion uses next-day RMSE with a 1% improvement
threshold; ties within 2% are broken on residual std, then on forecast
stability (mean day-over-day prediction jump).

## Optimization layer

Single-period newsvendor with demand ~ N(μ, σ²):

```
Q* = μ + σ · Φ⁻¹(CR)
CR = max( c_s / (c_s + c_w),  service_level_target )
```

With ₹55 shortage and ₹35 waste, the cost-optimal ratio is 0.611 (z ≈ 0.28),
but the 0.95 service-level target (z = 1.645) dominates. **In this
configuration the service-level floor always binds, not the cost economics.**
That is deliberate — a mess genuinely cannot run out — so the correct
description is "cost-optimal subject to a service-level floor," and
`NewsvendorOptimizer.recommend()` logs which constraint is active on every call.

Expected waste and shortage use the standard normal loss function
(`σφ(z) + (Q−μ)Φ(z)`), and realized outcomes are computed against actuals for
the feedback loop.

## Architecture

```
Simulator ──► Feature engineering ──► Candidates (RF / XGB / LGBM / Ridge /
                                       Ensemble / TFT)
                                              │
                                    Winner selection
                                              │
                                    Interval calibration
                                              │
                         Demand forecast ──► Newsvendor decision
                                              │
                                    Ingredient plan
                                              │
                              Feedback (actuals) ──► Nightly retrain
```

**Feature engineering** (`backend/features.py`): leak-free lags (1/3/7/14) and
rolling statistics computed shift-then-roll, calendar annotation, monthly-median
weather imputation, `ColumnTransformer` with median imputation for numerics and
one-hot with `handle_unknown="ignore"` for categoricals.

**Interval calibration** (`backend/calibration.py`): monotone bisection on a
multiplicative sigma scale so empirical coverage tracks the nominal 90%. Scales
are persisted in the model bundle and applied at inference.

**Explainability** (`backend/explainability.py`): tree SHAP for boosted models,
signed coefficient × value for Ridge, permutation importance as a global
ablation proxy, grouped into named driver categories for the dashboard.

**MLOps** (`backend/mlops.py`): APScheduler nightly retrain in Asia/Kolkata,
SQLite model registry, optional MLflow logging that no-ops when MLflow is absent.

## Quickstart

```bash
pip install -r requirements.txt
uvicorn backend.main:app --reload          # http://localhost:8000
```

```bash
cd frontend && npm install && npm run dev  # http://localhost:3000
```

On first startup the system generates the panel, trains all candidates, promotes
a winner, and writes plots to `data/figures/`.

Verify the simulator's structural assumptions:

```bash
python scripts/recovery_test.py
```

## Configuration

Key fields in `backend/config.py` → `ForecastConfig`:

| Field | Default | Notes |
|---|---|---|
| `data_source_mode` | `"simulator"` | `"simulator"` or `"ingested"` |
| `synthetic_period_days` | `365` | One academic cycle |
| `holdout_days` | `60` | Effective value is `min(60, max(n_dates//6, 30))` |
| `minimum_sigma` | `3.0` | Fixed floor, sized for the 50-meal series |
| `waste_cost` / `shortage_cost` | `35.0` / `55.0` | ₹ per meal |
| `service_level_target` | `0.95` | Binds over the cost ratio at these costs |
| `prediction_interval` | `0.90` | Nominal coverage |
| `promotion_improvement_pct` | `1.0` | Challenger must beat incumbent by this |
| `enable_cpu_tft` | `False` | TFT runs only with CUDA unless enabled |

In `"simulator"` mode the panel is regenerated only when it does not match the
current config (kitchen set changed, or the date span is short). The model
registry, predictions, decisions, and training runs are preserved across
regeneration, so champion/challenger and the feedback loop survive a retrain.

## Known limitations

Stated here rather than discovered later.

1. **Daily aggregate only.** `meal_session` exists in the schema but is
   hardcoded to `daily_aggregate`. Splitting into breakfast/dinner would make
   the Sunday-night vegetarian collapse (~0.55 multiplier, already a named
   constant in the generator) directly modellable instead of being absorbed into
   the −18% daily average. Blocked on the `UNIQUE (kitchen_id, date)` constraint,
   which would need to become a three-column key.

2. **Single seasonal cycle.** 365 days means every seasonal effect is observed
   exactly once. Seasonality cannot be identified independently of the
   particular year — a real limitation of one-cycle data, not a bug.

3. **Weather is synthetic unless `/ingest` is run first.** In simulator mode
   the pipeline never calls the ingestion layer, so `kolkata_weather_daily.csv`
   will not exist and the analytic Kolkata climate curve is used. Run
   `POST /ingest` once to overlay real Open-Meteo observations.

4. **The `"ingested"` path is not rescoped.** `build_processed_operations()`
   scales a public weekly food-delivery series to kitchen capacity. It runs, but
   it is a demand *proxy*, not mess data, and its per-row structure is much
   weaker than the simulator's. Dormant at the default config.

5. **`default_attendance_band` is constant.** All three hostels are `"high"`,
   so the column carries no signal. It is still stored in the DB and returned by
   `/kitchens`, though it is no longer a model feature.

6. **TFT is expected to lose.** With three series and one year of daily data,
   there is not enough cross-series structure for attention to pay for its
   parameters. It is retained as a challenger and reported honestly when it
   loses; it is skipped entirely without CUDA.

7. **Baseline edge cases.** The seasonal-naive baseline falls back to a
   per-kitchen expanding mean when fewer than 7 prior observations are available
   for a series in the evaluation window.
